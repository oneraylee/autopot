# Role
你是一位精通 TDD（测试驱动开发）和系统架构的高级技术专家。你的目标是为 AI 编程助手设计一套精确、可执行的开发步骤文档。

# Context
基于 ：
1. `docs/init` 目录下的全套项目文档（PRD、架构图、数据模型、编码规范等）
2. 你需要拆解系统并制定开发计划。

# Task
请在 `docs/dev_step/` 目录下生成一系列开发步骤文档。文档必须严格遵循 **“自底向上”**（Bottom-Up）原则，即：基础/工具库 -> 数据层 -> 业务逻辑层 -> 接口/表现层。

# File Structure & Naming
文档必须按执行顺序编号，格式为 `{序号}.{模块名}库/模块.md`。
示例：
- `docs/dev_step/0.总览.md` (总览与依赖拓扑)
- `docs/dev_step/1.Common库.md`
- `docs/dev_step/2.数据层.md`
- `docs/dev_step/3.业务逻辑层.md`
- `docs/dev_step/4.接口层.md`
...

# Document Content Guidelines (Crucial for AI Context)
每个模块文档必须包含以下三个部分，语言需极度精炼：

## 1. Context Requirements (上下文依赖)
* **必须**列出开发此模块前，AI 需要读取 `docs/init/` 中的哪些具体文档（精确到文件名）。
* *目的：让 AI 助手只加载必要的上下文，节省 Token。*

## 2. TDD Implementation Steps (TDD 执行步骤)
按原子粒度拆分步骤，每一步遵循 `Red -> Green -> Refactor` 循环。
格式如下：
- **Step [X]: [功能名称]**
    - `Task`: [简述要做什么]
    - `Test File`: [测试文件路径]
    - `Impl File`: [实现文件路径]
    - `Checklist`:
        - [ ] 编写失败的单元测试 (Red)
        - [ ] 实现最小代码通过测试 (Green)

## 3. Verification (验证标准)
* 列出该模块开发完成后的验收标准（如：测试覆盖率要求、关键接口响应）。

# Constraints
1.  **Token Efficient**: 不要重复 `docs/init` 中的内容，仅做引用（Reference）。
2.  **No Ambiguity**: 路径、类名、方法名需尽量明确。
3.  **Atomic**: 每个文档的开发工作量应控制在一个 AI Session 能处理的范围内。
